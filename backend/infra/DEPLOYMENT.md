# Dedicated BedtimeStories cloud environments

This scaffold has not been applied. On 2026-10-02 Google Cloud rejected creation of `bedtime-stories-staging-mz` because the personal account's project quota was exhausted. `bedtime-stories-prod-mz` is also only a proposed target. Existing unrelated projects must not be reused or deleted to bypass this gate. The example billing identifier is the verified personal **Private Projects** account; recheck ownership and billing eligibility before applying.

The module pins Google and Google Beta providers to 8.2.0 and separates staging/production with independent variable files and independent Terraform state. Foundation resources are created with `worker_image = null`; then build/push the worker, set its immutable image digest, and apply again to add the private service and scheduler. Keep state in a protected remote backend or encrypted administrator workspace. There are no API secrets or private keys in these variables or generated environment files. No Apple sign-in private key is placed in Terraform state.

## Deployment sequence after the quota gate is resolved

1. Create a protected per-environment state location and copy the appropriate `.tfvars.example` to an ignored `.tfvars`. Run `terraform init`, `terraform fmt -check`, `terraform validate`, and a reviewed `terraform plan -var-file=environments/staging.tfvars`. Apply that exact plan only after target/billing readback. Projects, buckets, Firestore, and KMS keys have destruction protection.
2. Build `backend/worker` and push `europe-west1-docker.pkg.dev/PROJECT/bedtime-voice/worker`; resolve the digest. Set `worker_image` to that digest and plan/apply again. Read back the service's runtime identity, IAM invoker check, concurrency 1, timeout 1800 seconds, memory 2 GiB, instance bound 2, and absence of public invoker bindings. Cloud Tasks rate is 1 dispatch/second, 2 concurrent, 30 attempts; each task's dispatcher supplies deadline 1800 seconds. Daily cleanup uses its own OIDC identity and base-service audience.
3. Register the exact output bucket using `register_output_bucket.py --project PROJECT --bucket PROJECT-audio --register --configure-cli`. Without these flags it performs readback only. The script verifies GCS `projectNumber` against Cloud Resource Manager before the Firebase `addFirebase` call and reads the linked resource back. [Official Firebase Storage registration API](https://firebase.google.com/docs/reference/rest/storage/rest/v1beta/projects.buckets/addFirebase) enables Firebase SDK/Rules support; there is no fabricated Terraform storage-link resource.
4. The `--configure-cli` flag runs the named Storage target binding for this exact bucket and writes ignored `.env.firebase.PROJECT.json` beside the repository's `firebase.json`, preserving its relative Functions/Firestore paths and assigning Storage rules to `cloud-audio`. Deploy with `firebase deploy --config .env.firebase.PROJECT.json --only firestore:rules,firestore:indexes,storage:cloud-audio --project PROJECT`. Read back the rules on **PROJECT-audio**, rather than the default bucket, and confirm authenticated A/B isolation; linking the bucket alone does not deploy rules. The original config remains useful for emulators.
5. Export `terraform output -json` to a private temporary file. `prepare_functions_env.py --outputs-json FILE` writes ignored `backend/functions/.env.PROJECT` with only resource IDs, runtime identities, and the worker's base URL. The script enforces `ENABLE_CLOUD_NARRATION=false`; reserved Firebase variables such as `GCLOUD_PROJECT` are provided by the runtime. Deploy with `firebase deploy --only functions:cloud-voice --project PROJECT`, then read back each function's intended `voice-api` service account.
6. Provision the exact Firebase Apple app/client config, enable Sign in with Apple using securely stored Apple provider credentials, register App Attest for this bundle/team, and enforce App Check on Firestore and Storage. These identity-sensitive steps are deliberately outside this Terraform scaffold. Keep the app and server feature gates off until physical-device Apple/App Attest and voice feasibility are verified.
7. Run the human-recording feasibility probe documented in `backend/WORKER.md`, verify provider create/get/style generation/delete using the actual worker service account, check quotas/cost, and listen on a physical device. Also invoke cleanup with its scheduler identity and verify private bucket grants, no download tokens, account/voice deletion, and cross-user denial with valid Auth/App Check. Enable staging first; production requires its own verified resources and client configuration.

## IAM boundary

The API service account can access Firestore, verify revoked Firebase Auth users and consumed App Check tokens, encrypt recordings with this KMS key, write/read/remove objects in the voice bucket, enqueue this queue, and act as this queue's invocation identity. It cannot decrypt recordings or read generated audio. The worker can use Firestore, revoke/delete users through a custom auth role, access objects in these two buckets, and encrypt/decrypt with this key. It receives the documented Agent Platform User role only in this dedicated project; the new preview Voices API's finer IAM permissions must be verified against live service responses before replacing that documented role with a custom inference role.

Queue and scheduler accounts only invoke the private Cloud Run service; the respective Google-managed service agents can mint their OIDC tokens. No account receives Owner/Editor, service-account keys, public object access, or public service invocation from this module. Firebase's build/deploy service agents are managed by the CLI and Google APIs; their deployment permissions must be checked during the first CLI deployment rather than assumed from runtime permissions. [App Check verifier role](https://docs.cloud.google.com/iam/docs/roles-permissions/firebaseappcheck), [Cloud Run authentication](https://docs.cloud.google.com/run/docs/authenticating/service-to-service).
